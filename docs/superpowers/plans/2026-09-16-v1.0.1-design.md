## 1. 任务一：删掉 `read_file` 的 `max_bytes`

### 现状（实测过的事实）

```python
class ReadFileParams(BaseModel):
    path: str = Field(..., description="要读取的文件路径")
    max_bytes: int = Field(64000, description="最多读取的字节数")

async def _read_file(path: str, max_bytes: int = 64000) -> str:
    truncated = target.stat().st_size > max_bytes
    data = handle.read(max_bytes)
    ...
```

两个闸门叠在一起，而**后面那个才是真的**：

| 层 | 闸门 | 谁看得见 |
|---|---|---|
| `_read_file` | `max_bytes`（默认 64000 字节） | 模型参数 schema |
| `Agent._run` | `truncate(out)` → `MAX_RESULT_CHARS = 8000` **字符** | 没人告诉过模型 |

对中文（3 字节/字）64000 字节 ≈ 21300 字，而出口只有 8000 字符：
**`max_bytes` 超过约 24000 之后完全无效**。实测模型试了 6万/20万/40万，
返回全是开头约 7000 字，为这个假旋钮烧掉数步。

（补一句精确的：那三次试探里只有第一次真读到了 64000 字节。40 万字节那次对 4.3MB 全书
**只在每个入口读 64KB** 这个意义上「无效」——真正的瓶颈是出口那道 8000，`max_bytes`
无论怎么调都够不着它。诊断不变：**参数描述承诺了一件它做不到的事**。）

### 决定：删掉参数（而不是"让它真的管用"）

另一条路（`max_bytes` 传入 `truncate`、把 8000 这个硬上限跟着它走）被否掉，理由三条：

1. **它会打破两条不变量**：`MAX_RESULT_CHARS` 是 spec §8 定的**"每个工具结果"**上限
   （`run_powershell` 的 `dir /s` 同样受它保护），不是"每个读文件"上限；
   而且真把出口开到 6 万字符，等于把上下文窗口交给模型自己的参数决定。**这是危险的方向。**
2. 8000 字符是**一整个系统**的属性，不是 `read_file` 一个工具的参数——它属于 `Agent`。
   把它做成 per-tool 旋钮，是把全局约束降级成局部选项。
3. 旋钮本身**没有使用场景**：没有"读文件但想要更少"的需求——想少读要靠 `offset`/`limit`（1.1.0），
   而 `max_bytes` 是按字节切的，天然切在多字节字符中间。**一个没人拧、拧了还切坏字的旋钮，就是负债。**

> **版本判断（新 semver 约定）**：删参数**不是破坏性变更**——唯一的消费者是模型，
> 它每轮重读 schema 自动适应（`HANDBOOK.md` §四 明写了这条边界），所以是 PATCH。
> 同理，把 `decode_text` 抽成模块级函数、以及将来重构 `MAX_RESULT_CHARS` 的用法，
> 都是**改 Python 内部结构，不动版本号**。

### 具体改法（最小的那一种）

```python
_READ_CAP_BYTES = 64000   # 内部上限：只 cut，不承诺。理由见注释

class ReadFileParams(BaseModel):
    path: str = Field(..., description="要读取的文件路径")

async def _read_file(path: str) -> str:
    ...
    truncated = size > _READ_CAP_BYTES
    data = handle.read(_READ_CAP_BYTES)
    decoded = decode_text(data, truncated=truncated)   # 抽出来只为可测；None = 二进制
    if decoded is None:
        return f"无法按 UTF-8 解码（可能是二进制文件）：{target}"
    if truncated:
        return f"{decoded}\n…[文件共 {size} 字节，这里只读了开头 {_READ_CAP_BYTES} 字节]"
    return decoded
```

（**不要把 `decode_text` 的返回值直接透传出去**——它可能是 `None`，进了
`truncate()` 就是 `TypeError`，会被 §9 的兜底伪装成"工具报错"。判断"是不是二进制"
与拼文案留在 `_read_file`。）

四个要点：

1. **字节上限保留为内部常量**，值不变（64000），只从"参数"降级成"实现细节"。
   它存在的理由只剩一条：**文件先按字节切，才能判断"末尾一个非法字节是不是我们自己切的"**
   ——这是现有二进制回退逻辑的前提（`data[:-1]`/`[:-2]`/`[:-3]` 重试）。
   顺手拿到一个副作用：**200MB 的日志文件不会被整个读进内存**。
2. **`decode_text(data, *, truncated)` 抽成模块级函数**，只为可测：现有两条测试
   （`test_read_file_truncation_mid_character_is_not_reported_as_binary`、
   `test_untruncated_binary_file_is_reported_as_binary`）正是靠传入小 `max_bytes`
   才构造出"切在多字节字符中间"的输入。参数没了，这两条测试会连着覆盖一起消失——
   抽个纯函数喂裸字节，覆盖保住，而且不再需要 64000 字节的测试文件。
3. **工具描述说实话**（这才是模型真正读得到的地方）：

   ```
   "读取一个文本文件的内容。一次最多返回 8000 字符；超出会截断并标注本次读到的长度
    ——没有可以调大这个上限的参数，不要为此重试更大的值。文件比这更大时会另有说明。"
   ```

   两句各治一个毛病：前半句把"标注里的长度只是本次读到的"说清楚（免得它把 8000
   或 64000 当成文件大小），后半句是**给模型看的负向约束**——它上次就是靠试参数
   烧掉的步数。**别为了精简把后半句删掉**：那正是这次要修的那条。而"文件更大时另有说明"
   指的就是 `_read_file` 自己那句真实大小标记。

   末句是**给模型看的负向约束**——它上次就是靠试参数烧掉的步数；前半句是
   "标注里的长度只是本次读到的"这个限定，免得它把 8000 当成文件大小。
4. **`truncate()` 一个字不改**，`MAX_RESULT_CHARS` 继续管所有工具。

### 为什么不顺手加 `offset`/`limit`

**它是功能新增（向下兼容，旧的调用方式照旧能用）→ `1.1.0`（MINOR）**，按 `HANDBOOK.md` §四
与 `backlog.md` 的归属都不该塞进这次。**这是范围决定，不是版本决定**——就算它按新约定
只算 PATCH，本次也不做（见 §8）。

（记一笔动作项，别丢：升级 tag 说明与 spec §14 要写清
**"8000 字符是唯一出口，内部 64 KiB 之外的文本从 1.0.1 起读不到，直到 1.1.0 加 `offset`"**。
1.1.0 的设计输入见 §10。）

## 2. 任务二：`norma.log` 挪出 CWD

### 现状

`cli.py:LOG_PATH = "norma.log"` → 写在进程 CWD。两个后果都实测到了：
用户工作目录被污染；日志出现在 `list_dir` 结果里，**模型把它当内容读**（白烧一步）。

### 决定：`~/.norma/audit.log`（单一固定位置）

```python
LOG_PATH = Path(os.environ.get("NORMA_LOG_PATH", "").strip()
                or Path.home() / ".norma" / "audit.log")
```

- **不用 Windows 专有的 `%APPDATA%`**：`~/.norma/` 在两个平台上都是同一条路径，
  代码里不必出现平台分支。（`Path.home()` 在本机 = `C:\Users\Administrator`，已实测。）
- **`setup_logging()` 前先 `mkdir(parents=True, exist_ok=True)`**：`basicConfig(filename=...)`
  遇到不存在的父目录是 `FileNotFoundError`，直接崩在启动那一刻。
- **顺带解决一个既有的小坑**：`logging.basicConfig()` 看到根上已有 handler 就整个跳过。
  改为**显式构造 `FileHandler` 再 `addHandler`**，行为不再取决于外部有没有配过 logging
  ——这也是现有那条 `test_setup_logging_really_raises_the_root_level` 测试正在绕的坑
  （它得手动摘掉根 handler 才测得到真实行为）。**不额外做防重复调用**，YAGNI。
- **`NORMA_LOG_PATH` 环境变量**：一行，兼作测试隔离（现有 `test_cli.py` 用 `monkeypatch.chdir`
  躲日志，路径固定后 chdir 失效，会往真 `~/.norma/` 里写）。**不给它写进 README 的配置表**
  ——它是测试与调试用的逃生舱，不是用户配置项。
- **CWD 里的 `norma.log` 不迁移、不清理**：老文件是用户的，不该由代码删。
- CLI 启动横幅打**解析后的完整路径**（`审计日志：C:\Users\...\.norma\audit.log`），
  README 同步改成"每次工具调用都记入 `~/.norma/audit.log`"。
- `.gitignore` 的 `norma.log` 保留（旧文件还在用户工作目录里，且这条无害）。

## 3. 任务三：拒绝文案要能引导换工具

### 现状

`permission.py` 返回 `"用户拒绝了这次操作"`。模型读到的信息是"这次操作"，
而**它不知道"这次"指的是哪个工具、也不知道这个拒绝是暂时的**——
于是理解成"这台机器上 PowerShell 不可用"，连试 4 种命令，最后拿 `echo test` 试探环境。
4 步烧在"确认环境坏没坏"上。

### 决定：把工具名和"换个办法"写进回填文本

```python
return (f"用户拒绝了这次 {tool.name} 调用。"
        f"这不是工具坏了或环境不可用，而是用户这一次不允许。"
        f"请改用其他工具或换个思路完成任务。")
```

三个要素缺一不可：

| 要素 | 治什么 |
|---|---|
| `这次 {tool.name}` | 模型知道**拒绝的确切对象**是这一次调用，不是整个工具、更不是整台机器 |
| `不是工具坏了或环境不可用` | 直接掐掉那次"4 步试探环境"的推理起点 |
| `改用其他工具或换个思路` | 给出去处；只堵不疏，模型会原地重试同一个工具 |

`check()` 本来就拿着 `tool` 对象（签名是 `check(tool, args, ask)`），**零新增参数**。

### 一处不写

**不在文案里许诺"下次问就能过"。** 权限策略是 `POLICY` 表的事，`check()` 不该替策略做承诺。
**也不加"是否询问过用户"的区分**——`check()` 拿到的 `bool` 分不清"用户说不"与
"EOF/远端断线一律按拒绝"，那是 §10 的 fail-closed 路径，属于 v2 权限往返的设计范围。

## 4. 任务四：system prompt（现在完全没有）

### 现状

`Agent.run()` 只 append `{"role": "user"}`，**`messages` 里从来没有 system 消息**。
冒烟时中文提问，模型第一句用英文回答再转中文——它没有任何理由知道该用中文。

### 决定：默认 prompt 属于内核，位于 `messages[0]`，由 `Agent` 拥有

```python
DEFAULT_SYSTEM_PROMPT = """..."""

class Agent:
    def __init__(self, llm, ask_permission, tools=None,
                 max_steps=DEFAULT_MAX_STEPS, system_prompt=None):
        self.system_prompt = DEFAULT_SYSTEM_PROMPT if system_prompt is None else system_prompt

    async def run(self, user_input: str) -> AsyncIterator[Event]:
        self._ensure_system_message()      # 只钉一次
        self.messages.append({"role": "user", "content": user_input})
```

四个决定，逐个说理由：

1. **默认值在内核（`agent.py`），不在 `cli.py`。**
   若默认值由客户端提供，下一个客户端（v2 的浏览器客户端）会再次漏掉它——
   "中文提问先用英文答"会原样复现。内核给可用默认值、调用方可覆盖，是这里唯一稳的形态。
   **没有破坏内核纪律**：`Agent` 依然不读环境、不建网络客户端、不读配置文件；
   一个模块级字符串常量是内核自己的默认行为。
2. **`system_prompt=None` 表示"用默认"，传 `""` 表示"真的不要"。**
   `None` 与空串必须分开——空串是"关闭"这个明确的意图，`None` 是"没表态"。
   测试与将来的自定义客户端都需要前者。
3. **放在 `messages[0]`、`run()` 里只钉一次**，判据是**第一条是不是 system 消息**
   （`if self.messages[:1] and self.messages[0]["role"] == "system": return`），
   而不是记一个 `self._system_initialized` 布尔。
   这样"客户端在构造后自己往 `messages` 里塞了东西"（比如将来加载的历史）不会被我们覆盖，
   也不需要维护第二份状态。多轮 `run()` 不重复插入。

   > **判据看位置、不看存在**（实现时修正的）：只查"有没有 system 消息"的话，
   > 一个把历史恢复进 `messages`、system 却在中间的客户端会让默认 prompt 被整个跳掉
   > ——而那正是 v2 恢复会话历史时的形态，缺陷会悄悄回来。
   > 客户端自己带的 system 消息（包括一条空的）照样优先：`messages` 是唯一事实来源。
4. **内容只有 5 类，不写更多**（prompt 不是许愿池，写长了会跟工具行为打架）：

   | 行 | 治什么 |
   |---|---|
   | 你是 norma，跑在用户本机的助手 | 身份，兼默认语种锚点 |
   | **始终用中文回答**，除非用户明确要求别的语言 | 直接治冒烟那条（"一句「始终用中文」可能就够"） |
   | 读文件/列目录用对应工具，**不要用 `run_powershell` 去读文件** | `run_powershell` 是 exec 风险，每次都会弹确认框——这条既省步数又少弹框 |
   | 一次读文件最多返回 8000 字符，超了会被截断标注；**不要重试更大参数** | 与任务一同源：**唯一能提前告诉模型"没有那样的参数"的地方** |
   | 不确定就说不确定，**绝不编造**内容 | 实测它已经做对了（"避免我编造后面的内容"），把好行为写成契约 |

   **不写**步骤格式、不写工具清单、不写 "you are a helpful assistant" 式套话——
   工具清单由 schema 给，套话只烧 token。

> **版本判断（旧约定下这里曾经是个纠结，新约定下没了）**：加 system prompt 修的是
> **观察到的缺陷**（「中文提问，模型第一句用英文回答」，`backlog.md` 摩擦表 2026-09-16 有现场），
> 而且**不破坏任何依赖方**——事件协议没动、工具 schema 没动。所以它是 PATCH → `1.0.1`。

### 需要承认的一处代价

`messages` 从此**不以 `messages[0] == user` 开头**，现有 7 条按索引/角色列表写死的断言
（`test_tool_result_is_backfilled_into_messages`、`test_finished_text_is_not_duplicated_into_messages_twice`
等）都会跟着漂一位。

**实现时改成了另一种做法**（比原计划好，故记录在此）：不去把 7 条断言逐个改成 `[1:]` 视角，
而是让 `scripted()` **默认关掉 system 消息**（`system_prompt=""`），
system prompt 自己的用例再显式打开。两个好处：那 7 条断言仍在验它们本来要验的东西
（**对话形状**），不必为无关的索引漂移加噪音；而"开着 system 消息时形状对不对"
由单独一条用例钉住。代价是**开启态下只有 7 条用例覆盖**（6 条单元 + 1 条真子进程 CLI；
实测法：把 `DEFAULT_SYSTEM_PROMPT` 换成空串，红的正好这 7 条），
将来"只在有 system 消息时才坏"的回归可见面偏窄——这条已经写进 §5 的取舍表。

## 5. 已知取舍（打完 tag 要写进 spec §14 与 tag 说明）

| 取舍 | 代价 | 升级路径 |
|---|---|---|
| `read_file` 无 `max_bytes`，出口恒为 8000 字符 | 想少读/跳读做不到 | `offset`/`limit`（1.1.0，backlog 已升级为「待清」） |
| `read_file` 内部 64 KiB 上限（不可调） | 超过 64 KiB 的**纯文本**尾部读不到（此前也读不到，因为出口只有 8000 字符）。**现在至少会说清楚**（`…[文件共 N 字节，这里只读了开头 M 字节]`），而不会让模型把"原文 64000 字符"当成文件大小 | 与 `offset` 同批解决；或改流式解码 |
| 日志固定 `~/.norma/audit.log`，无轮转 | 长期使用会持续增长 | 接入 `RotatingFileHandler`，或客户端提供查看入口 |
| `NORMA_LOG_PATH` 未进 README | 用户不知道有逃生舱 | 真有第二个实例/沙箱需求时再文档化 |
| `setup_logging()` 不防重复调用 | 调两次会挂两个 handler、同一行写两遍，前一个句柄不关（真实入口只调一次，测试自己收尾） | 一行 `any(isinstance(h, FileHandler) and Path(h.baseFilename) == path …)` 早退 |
| 日志目标不可用时直接抛裸 traceback | 目录被占用/父路径是文件时启动即崩，只有 `配置错误：` 那种文案缺失 | 与 `Config.from_env()` 的错误处理对齐，包一层友好提示 |
| 拒绝文案不承诺"再问一次可能过" | 模型不会主动重试（**这正是想要的**） | v2 权限往返设计时，把"可重试"做成策略层的信息 |
| system prompt 内容是硬编码中文 | 想换语种/换人格要改代码或构造 `Agent` 时传入 | 规则文件式配置（与权限策略同一批） |
| 测试里 `scripted()` 默认关掉 system 消息 | **"只在有 system 消息时才坏"的回归，可见面只有 7 条用例**（6 单元 + 1 真子进程；实测：把 `DEFAULT_SYSTEM_PROMPT` 换成空串，红的正好是这 7 条） | 若真出现这类回归，把 `scripted()` 默认翻回开启并接受索引漂移 |

## 10. 记给 1.1.0 的设计输入（`offset`/`limit`）

这次不做，但已经查过的东西别丢：

1. **瓶颈不是 8000，是"没有游标"。** 实测（`_norma-experiment/report.txt:113`）：
   16848 字符的 `ch01-05.txt`，模型调了 **3 次** `read_file`（3 × 8000 = 24000 > 16848，
   **够覆盖全文**），却只读到开头一半——因为三次都从第 0 个字符开始，返回同一段。
   **线性读取没有游标时，重试同一个工具永远在原地打转。**
2. **`offset` 按字符、不按字节。** 模型脑子里数是字符（它自己的诊断就写"没有 offset 参数"）；
   字节语义会让它算不准，且会重新引入"切在多字节字符中间"那一类 bug。
3. **返回值要带进度**，如「已返回 8001-16000 字符，共 16848」——模型据此自己判断还有没有下一段，
   不用再烧一次调用去试探（这正是它上次烧步数的形态）。
4. **上限先别做成参数。** 让模型自己决定"一次读多宽"等于把上下文窗口的控制权交给它，
   和 `max_bytes` 是同一类错误。**分页给游标，不给宽度。**
5. **真要动 8000，先量再动。** 算过：8000 中文字符 ≈ 4800 token
   （DeepSeek 官方口径 1 中文字符 ≈ 0.6 token），占 `deepseek-chat` 128K 窗口的 3.75%——
   **它从来没接近过自己的天花板**，所以那个数一直是"看着合理"而非算出来的。
   要改就用实测：让它读一章、记 `usage.prompt_tokens`（唯一真值，0.6 只是估算）再定。
6. **`MAX_RESULT_CHARS` 现在是全局默认，同时管着 `run_powershell`。** `dir /s` 那种"洪水"
   需要这个上限，读文件不需要——真要调，得**拆成按工具区分**，而不是调那个全局常数。

> 上面 1/2/3/4 是从 `HANDBOOK.md` §一 那条「每章都在 norma 8000 字符的读取上限内」反推出来的：
> **切章是按 8000 切的，这个数已经是下游的既成事实**，不再只是内部常量。
