## 0. 一句话

v1.0.1 把「读不完」这件事说清楚了；v1.1.0 让它**真的能读完**——
**给游标，不给宽度**。

## 1. 问题：瓶颈不是 8000，是没有游标

实测（`_norma-experiment/report.txt:113`，16848 字符的 `ch01-05.txt`）：

```
模型调了 3 次 read_file          （3 × 8000 = 24000 > 16848，够覆盖全文）
结果：只读到开头约一半
原因：三次都从第 0 个字符开始，返回的是同一段
```

**线性读取没有游标时，重试同一个工具永远在原地打转。** 所以这不是"上限太小"的问题，
是"读不到第二段"的问题——加多少个 0 都没用。

模型自己诊断出了这一点（原话）："`read_file` 只能从文件开头返回内容，没有 offset 参数"。

## 2. 接口：只加两个参数，语义写死在描述里

```python
class ReadFileParams(BaseModel):
    path: str = Field(..., description="要读取的文件路径")
    offset: int = Field(0, description="从第几个字符开始读（0 起算，默认从头）")
    limit: int = Field(MAX_RESULT_CHARS, description=f"最多返回多少字符（默认且最大 {MAX_RESULT_CHARS}）")
```

### 决定 1：`offset` 按**字符**，不按字节

模型的诊断写的是"没有 offset 参数"，它脑子里数的是字符。字节语义会让它算不准，
而且会把 v1.0.1 刚清掉的那类 bug（按字节切在多字节字符中间）请回来。

**代价（写进 §5 取舍表）**：字符语义要顺序解码才能定位，所以 `offset` 很深时读得慢
（见决定 4 的 64 KiB 边界）。

### 决定 2：**给游标，不给宽度** —— `limit` 被夹到 8000

`MAX_RESULT_CHARS = 8000` 是**每个工具结果**的硬上限（`run_powershell` 的 `dir /s`
同样受它保护），不是 `read_file` 的私有参数。让模型用 `limit=100000` 把这个出口顶开，
等于把上下文窗口的控制权交给它——**那正是 v1.0.1 删掉 `max_bytes` 的同一个错误**。

所以：`limit` 描述里写明"默认且最大 8000"，实现里夹住（`min(limit, MAX_RESULT_CHARS)`）。
模型想多读就**往后翻页**，而不是要求一次给更多。

> 那为什么还留 `limit`？——因为小步读是真实需求（"我只想要这一节的标题"），
> 而它的**上界**不归模型管。一个只能往小里调的旋钮不会伤人。

### 决定 3：返回值带**进度标记**，而且放在**开头**

```
…[第 8001-16000 字符，共 16848 字符]\n<正文>
```

三个理由：

1. **模型据此决定还要不要翻页**，不用再烧一次调用去试探"到底有没有下一段"
   ——它上次烧步数就是这个形态。
2. **必须放开头**：工具结果还要过 `Agent` 那层 `truncate()`（只留前 8000 字符），
   追加在末尾的标记会被吃掉。**v1.0.1 的终局审查正好抓到过这个错**（`read_file`
   那句文件大小标记写在末尾 = 写了等于没写），别再犯第二次。
3. 它和 `truncate()` 的 `…[已截断，原文 N 字符]` **语义不同、不冲突**：
   一个是"这是文件的哪一段"（页），一个是"这一段本身还被砍了"（内容超限）。
   两个都在时，模型拿到的是它需要的两件事。

### 决定 4：读取仍受 64 KiB 字节上限约束，且**如实说明**

内部 `_READ_CAP_BYTES = 64000` 保留。它是缓冲区，不是承诺——但当模型要的区间
落在它之外时，返回里必须说清，不能默默给一段短的：

```
…[第 64001- 字符起，共 N 字节；只有开头 64000 字节可读]\n<正文>
```

**代价**：如果 `offset` 对应的字符位置在 64000 字节之后，就读不到。对小说场景
（按 8000 字符切好的章文件，每章 8-30 KB）这不构成阻塞；对超大文件它会成为墙——
**写进 §5 取舍表，升级路径是流式解码**。

### 决定 5：`offset` 越界时说清楚，而不是返回空串

```
偏移 20000 超出文件长度（共 16848 字符）
```

空串对模型是零信息（"读到了空的"和"读不到"分不清），它多半会再试一次——
又是一次白烧的调用。

## 3. 实现：整块解码 + 字符切片（不手搓增量分块）

```python
async def _read_file(path, offset=0, limit=MAX_RESULT_CHARS):
    target = Path(path).expanduser()
    if not target.is_file():
        return f"文件不存在：{target}"

    size = target.stat().st_size
    with target.open("rb") as handle:
        data = handle.read(_READ_CAP_BYTES)

    text = decode_text(data)                      # None = 不是 UTF-8 文本
    if text is None:
        return f"无法按 UTF-8 解码（可能是二进制文件）：{target}"
    if len(text) == 0 and data:                   # 只可能是"整块都是半个字符"
        return f"无法按 UTF-8 解码（可能是二进制文件）：{target}"

    total = len(text)
    if offset >= total:
        return f"偏移 {offset} 超出文件长度（共 {total} 字符）：{target}"

    limit = min(limit, MAX_RESULT_CHARS)
    chunk = text[offset:offset + limit]
    cut_by_head_cap = size > _READ_CAP_BYTES
    cut_by_limit = offset + limit < total
    marker = (f"…[第 {offset + 1}-{offset + len(chunk)} 字符，共 {total} 字符"
              f"{'；文件只读了开头 ' + str(_READ_CAP_BYTES) + ' 字节' if cut_by_head_cap else ''}"
              f"{'，后面还有' if cut_by_limit else ''}]")
    return f"{marker}\n{chunk}"
```

**为什么是"整块解码 + 切片"而不是增量分块解码**：字符语义的 offset 需要按字符数
数过去，而 UTF-8 是变长的——真要分块就得处理"块首块尾各残留半个字符"，
那是 v1.0.1 那个 `decode_text` 回退逻辑的**两倍复杂度**，而且每一步都要新测试。
64 KiB 对本章节规模的文件是毫秒级，"读整块再切"换来的是**没有新 bug 面**。

> `ponytail:` 整块读进内存再切片；若真出现"必须读 1 GB 文件的第 900 MB 处"的需求，
> 再改成流式解码 + 字节游标（那时才值得付分块解码的复杂度）。

`_decode_or_none`（原 `decode_text`）顺带简化：整块读之后，那个 `truncated` 参数用不上了
——它原本用来区分"我们自己在块尾切出的半个字符"与"文件本身坏"。**但回退本身不能删**：
读取上限仍可能落在多字节字符中间（中文每字 3 字节、64000 不是 3 的倍数，这是常态），
而且**只在出错区间顶到缓冲区末尾时才退**——盲目退 1/2/3 字节会把 `b"abc\xff\xfe"`
变成 `"abc"` 返回，那是把二进制当文本悄悄读出来（v1.0.1 特意保住的判断）。

## 4. 系统提示词与工具描述

**工具描述**（模型唯一能提前读到的地方）必须说清三件事：

```
"读取一个文本文件的内容，可以指定读哪一段。offset 是起始字符位置（0 起算），
limit 是最多返回的字符数（默认且最大 8000，开头的进度标记也算在内）。
返回内容开头会标明这是第几到第几个字符、后面还有没有——文件比一次能读的长时，
把 offset 设成已读的字符数接着往下读，不要重复读同一段；也没有能把上限调大的参数。"
```

**system prompt** 加一句：**"长文件要分段读完：接着上次读到的地方继续，就把 offset
设成已读的字符数；不要重复读同一段。"**

> 两处都要动，因为它们是模型在**不同时刻**读到的：描述在每轮 schema 里，
> prompt 在最前面。**而且必须说同一句话**——这条在实现时真栽了一次，值得记住：
>
> 描述一度被我写成"把 offset 设成**上次读到的**字符数"。读起来是"上一页有多宽"
> （7965），而 prompt 写的是"**已读的**字符数"（累计 15934）。照前者算，模型
> **永远重读第二页**（审查用真 Agent 复现：8 次调用反复拿同一页）。
> 最要命的是**135 条测试全绿**——两边都含"offset"这个词就够了。
>
> 教训：**光有"两处一致"的约定不够，得有一条测试盯着那个词**。现在
> `test_the_prompt_and_the_description_teach_the_same_paging` 同时拒绝页宽语义
> （上次/本次读到的字符数）与字节语义，变异复验过（改回去 → 2 条红）。

## 5. 已知取舍（打完 tag 要写进 spec §14 与 tag 说明）

| 取舍 | 代价 | 升级路径 |
|---|---|---|
| `offset` 按字符数，需要顺序解码定位 | `offset` 很深的读取要解码整块（毫秒级，但线性） | 流式解码 + 字节游标；或按行号寻址 |
| 读取仍受 64 KiB 内部上限 | 字符位置在 64000 字节之后的区间读不到（对按 8000 字符切好的章文件无影响）。**现在会如实说明**，不会默默给短的 | 流式解码；或按 `offset` 直接 seek（需处理字符边界） |
| 单次仍最多 8000 字符 | 想一次读完长文件做不到 | `MAX_RESULT_CHARS` 按工具区分（读文件放宽、`run_powershell` 守 8000）——**要先量 `usage.prompt_tokens` 再定数值** |
| `limit` 能被模型调小、不能调大 | 无实际代价（只会让它读少一点） | — |
| 双截断标记（页标记 + `truncate` 标记）可能同时出现 | 输出略啰嗦；两句话语义不同、不冲突 | 若实测模型混淆，合并成一个标记 |
| 区间读取只能按字符，不能按行 | 模型要"读第 12 章"得自己换算字符位置——但它本来就是靠字符数推的 | 行号参数（另一个功能，等真实需求） |

### 任务 1 的测试清单（**覆盖必须钉住"翻页能读完"**）

- **核心**：16848 字符的文件，`offset=0/8000/16000` 三次读**拼起来等于原文**
  ——这条直接对应实验里的失败（三次读同一段）。没有它，读到的仍可能是三段开头。
- `offset` 按字符不按字节：混排 1/2/3/4 字节字符，从某个 `offset` 读出来的第一段
  必须与 `text[offset:offset+n]` 逐字相等（按字节实现会在这里错位）。
- 单次最多 8000：`limit=99999` 被夹到 8000。
- `limit` 调小有效：`limit=10` 只回 10 个字。
- 末尾一页：`offset` 落在最后一页时，标记说明"到底了"（没有"后面还有"）。
- 越界：`offset` = 文件长度、`>` 文件长度 → 说清总长度，不返回空串。
- 负数 `offset`/`limit<=0` → pydantic 校验拒绝并回填 `参数错误`。
- 进度标记**在开头**：过 `Agent.execute` 断言模型收到的内容以标记开头。
- 跨模块（任务 2）：走 `Agent` 读一个 40000 字符的文件，断言第二页内容与第一页**不同**
  且含有第二页应当有的那句话——这是"翻页真的往前走"的端到端证明。
- 既有的 read_file 用例（缺文件、二进制、超 64 KiB、标记穿 truncate）全部保持绿。

## 9. 需要你确认的一处（其余我按上面的决定走）

**`limit` 要不要留？** 设计输入 §10 第 4 条的原话是"上限先别做成参数——**分页给游标，
不给宽度**"。我的实现是**留 `limit` 但把它夹在 8000**（可以往小调、不能往大调），
理由是"小步读"是真实需求，而窄旋钮不伤人。

若你要更彻底的版本：**只加 `offset`，完全不加 `limit`**——每次固定 8000，
少一个参数、少一条描述、少一组测试。代价是模型没法"只读标题那 200 字"。

我推荐留 `limit`（夹住），但这条是你的判断。
