**这份文件是「怎么工作」，不是「要做什么」。** 要做什么在 `docs/backlog.md`。

配套关系：

| 文件 | 装什么 | 谁在读 |
|---|---|---|
| **`docs/backlog.md`** | 使用摩擦 / 待清 / 想法 —— **要做什么** | 每次开工 |

## 一、本机环境（换会话/换机器时先看这一段）

这台机器有几个坑，踩过一遍，别再踩：

| 坑 | 对策 |
|---|---|
| `python` 是 **0 字节的 Microsoft Store 占位程序**，运行返回 9009 | 一律用 **`E:\learning\ai\norma\.venv\Scripts\python.exe`**；`norma` 命令用 `.venv\Scripts\norma.exe` |
| 真实 Python 在 `E:\tools\python\`，**不在 PATH** | 同上。建 venv 用 `E:\tools\python\python.exe -m venv .venv` |
| `origin` 指向 `githubproxy.cc`，**它只代理拉取，不支持 push** | 推送走本机 Clash：<br>`git -c http.proxy=http://127.0.0.1:7890 push https://github.com/DestinyMiner/norma.git main` |

| 用 PowerShell 的 `Get-Content`/`Set-Content` 读写源码会**按 GBK 往返破坏 UTF-8** | 改文件一律用编辑工具，不要用 PowerShell 文本 cmdlet |
| PowerShell 的 `>` 会把原生命令输出**转码成 UTF-16LE** | 要检查真实字节就用 Python 子进程的裸句柄 |

## 二、会话怎么切

**按任务切，不按角色切。** 会话的单位是「**一个能关闭的目标**」，不是「一个职位」。

| 会话类型 | 什么时候开 | 开场白 | 什么时候算完 |
|---|---|---|---|
| **里程碑** | 要做新东西（如传输层） | 「读 `backlog.md`、`HANDBOOK.md` 和 spec §17，我们来做 X」 | 走完设计→计划→实现 → 打 tag → 更新 backlog |
| **清扫** | 「待清」攒了几条 | 「读 `backlog.md` 和 `HANDBOOK.md`，清掉这几条」 | 那几行删掉 |
| **方向** | 每个里程碑**开始前** | 「读 spec + `backlog.md` + `git log`，问：**我们还在做对的事吗？**」 | 结论写进 spec |

**「方向」这一类是唯一容易被跳过的，但最值钱**：里程碑会话审的是「你有没有按计划做」，
**没有人在审「计划本身对不对」**。一次方向会话 = 一场短对话，换来的是避免做错整个里程碑。

**不要为「监督」建常驻 agent。** 监督已经在流程里了（每个任务都有独立审查者）。
常驻角色会变成你要维护的另一件事。

## 三、分工（人和 AI）

| | 谁做 | 产出 |
|---|---|---|
| **实验** | AI | 可复现的机制记录：跑几次、几步、第几步崩、什么时候开始重复劳动 |
| **使用** | 人 | **三行现场**：我想干什么 / 它干了什么 / 别扭在哪 |

**「别扭」是人独有的数据**——AI 采集不到，因为它没有体感。反过来，「跑 5 次几次成功」是 AI 独有的——人没必要手搓。

**人不需要写 bug 报告。** 诺玛已经把每次工具调用写进 `norma.log` 了；
人只要产出现场，**分析是下一阶段的活**。

## 四、版本与提交约定

> **这是个人约定，跨仓库通用**，不只在 norma 里。新建仓库时把这节抄过去。
> **采用标准 semver**：`MAJOR.MINOR.PATCH`。

| 位 | 含义 |
|---|---|
| **MAJOR** | **破坏性变更**——依赖方会坏 |
| **MINOR** | **向下兼容的功能新增** |
| **PATCH** | **向下兼容的 bug 修复与优化** |

**判断的关键不是「我改了什么」，而是「有没有人会坏」。** 所以先回答一个问题：**谁是依赖方？**

norma 的依赖方有三类，各自依赖不同的东西：

| 依赖方 | 依赖什么 | 变了会坏吗 |
|---|---|---|
| **将来的客户端**（Electron / 安卓 / 鸿蒙） | **事件协议**（`events.py` 的 5 种事件） | **会坏** → MAJOR |
| **模型** | **工具的名称与参数 schema** | **不会坏**——它每轮重读 schema，自动适应 |
| 你自己 | CLI 的输入输出 | 顶多是习惯变了，不算接口 |

**由此得到判断规矩**：

```
事件协议变了（改字段、改语义、删事件）  → MAJOR
加新东西，旧的都还在                    → MINOR
把已有的修对                            → PATCH
```

**两条容易搞错的边界**：

- **工具参数的变化不算破坏性变更**——因为唯一的消费者是模型，而它每轮重新读 schema。
  所以「删掉 `read_file` 的 `max_bytes`」是 PATCH，不是 MAJOR。
  （但如果将来有客户端把工具列表**渲染成一个固定 UI**，这条就要重新判——那时工具 schema 也有会坏的依赖方了。）
- **Python 内部的类与函数不算公共接口**（`Agent` / `LLM` / 工具函数……）——
  它们没有外部消费者，**重构它们不动版本号**。

**发布动作**（norma 的做法，别的仓参照）：

1. 同时升 `pyproject.toml` 的 `version` 和 `src/norma/__init__.py` 的 `__version__`——两处必须一致，否则 `pip show` 和 tag 会打架
2. 用**附注 tag**（`git tag -a vX.Y.Z`），把「这个版本承诺什么、不承诺什么」写进 tag 说明——将来 `git tag -n99 -l` 就能看回来
3. 推送按「一、本机环境」里的 Clash 命令走

## 五、会话开工前读什么

1. **`docs/backlog.md`** —— 要做什么、撞到过什么（3 分钟）
2. **本文件** —— 怎么工作（3 分钟）
3. **spec §17** —— `docs/superpowers/specs/2026-09-15-norma-agent-kernel-design.md`
   的 §17（v2 做什么、不做什么、三个待答的设计问题）
4. `git log --oneline -20` —— 最近发生了什么

**这四份读完就能冷启动，跟你隔了 1 天还是 2 周无关。** 所以：**长会话可以放心关掉**——
决策该由文件驱动，不该由"我还记得聊过什么"驱动。

## 六、会话收尾时做什么

**把状态写进文件，不要留给下一次对话去记。** 具体地：

| 产生了什么 | 写到哪 |
|---|---|
| 使用中撞到的摩擦 | `backlog.md` 的「使用摩擦」表 |
| 决定要做的事 | `backlog.md` 的「待清」，或直接进 spec |
| 决定**不做**的事 | spec 的「§14 已知取舍」表（**带上升级路径**） |
| 做完的事 | 把 `backlog.md` 里对应那行删掉 |
| 只在对话里说过的策略/约定 | **补进本文件**（这一节和版本约定都是这么来的） |

> 一份没人读的 backlog 等于没有。所以 `backlog.md` 里只放**真会做**的事——
> 宁可短，宁可空，也不要攒成一份没人看的清单。
